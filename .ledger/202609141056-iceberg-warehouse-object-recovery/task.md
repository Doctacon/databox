## Agreed protection contract

1. **Existing warehouse bucket only.** Target the bucket configured by `DATABOX_AWS_S3_BUCKET`, not the catalog-backup bucket. Enable bucket-wide versioning without bucket creation/replacement/destruction, `force_destroy`, warehouse relocation, or rewriting existing objects. Existing `null` versions are valid; enablement cannot recreate history already lost.
2. **30 noncurrent days.** Use `NoncurrentVersionExpiration` with `NoncurrentDays=30`, bucket-wide, not current-object age expiration or a keep-N substitution. The clock starts when a version becomes noncurrent. Expiration is permanent, UTC-rounded and asynchronous, not an exact 720-hour deletion promise or immutable minimum retention. Already-old noncurrent versions may become immediately eligible, without a new grace period.
3. **Preserve existing behavior.** Inventory and preserve existing lifecycle rules and policy statements. Conflicting retention or another owner's data blocks adoption for a user decision; do not silently choose a prefix exception. Add no current-object expiration, transitions, delete-marker cleanup, multipart-abort rules, or Iceberg maintenance jobs.
4. **Root-only retention controls.** Add no Allow. Deny every non-root principal exactly `s3:DeleteObjectVersion` on the warehouse object ARN and `s3:PutBucketVersioning`, `s3:PutLifecycleConfiguration`, `s3:PutBucketPolicy`, and `s3:DeleteBucketPolicy` on the bucket ARN, using `ArnNotEquals` on `aws:PrincipalArn` against only the exact account-root ARN. This closes direct-writer, known role-session and unknown cross-account role paths. Ordinary `s3:PutObject` and `s3:DeleteObject` remain allowed; named-version and delete-marker removal do not. Bucket deletion, Object Lock and unrelated bucket settings remain outside this narrow guarantee.
5. **State the guarantee accurately.** Protected historical versions cannot be manually purged and retention controls cannot be weakened by non-root principals. Account root and S3 Lifecycle remain intentional permanent-deletion paths. Non-root principals with existing version-read and object-write access may still promote an old version as a new current object; this is not root-only recovery. Current-object deletion/corruption, version storms, storage cost, root/account compromise, loss of the bucket/account and detection after expiration remain outside the guarantee.
6. **One infrastructure owner.** Adopt only required settings through existing `infra/recovery/`, preserving catalog resource addresses, state, roles and permissions. No competing lifecycle/policy resources or blind replacement. Any necessary state-only imports need separate reviewed authorization. Preserve ignored local state, mode `0600`, FileVault protection and cleanup exclusion; do not add a backend or second state copy.
7. **Separate rollout approval.** Require a fresh exact plan/hash, independent review and explicit apply approval; drift invalidates approval. Explain added version-storage cost (no approved numerical cap), irreversible first enablement and old-history expiration exposure. Coordinate an authorized maintenance owner for AWS's recommended 15-minute no-PUT/DELETE window after first enablement; no implicit authority to stop jobs/services/CI. Recheck current AWS guidance before rollout.

Do not reuse catalog-backup credentials for warehouse operations. Preserve existing catalog startup gate, manual authenticated WAL catch-up and accepted durability gap; do not claim continuous five-minute off-machine RPO. The catalog's 60-minute RTO is not a warehouse recovery guarantee.

Do not mutate authoritative data, source/model semantics, active-stack lifecycle, prior catalog-drill resources, private evidence, personal files or `uv.lock`. Version retention alone is not full warehouse PITR or a universal 30-day table-recovery guarantee.
